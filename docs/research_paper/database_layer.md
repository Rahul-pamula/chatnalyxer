# III.C. Database Layer

This subsection delineates the architecture, structural schema, and operational mechanics of the Persistent Storage Layer within the Chatnalyxer ecosystem. As the central repository for all extracted organizational data and user state, the database layer must balance the competing requirements of high-velocity concurrent writing, complex temporal querying for the scheduling engine, and absolute adherence to stringent data privacy and security paradigms.

### 1. PostgreSQL Schema and Architectural Selection

The foundational bedrock of the Chatnalyxer storage layer is PostgreSQL, a highly robust, open-source object-relational database management system (ORDBMS). The selection of PostgreSQL over NoSQL alternatives (such as MongoDB) or lighter relational databases (such as SQLite) was driven by rigorous architectural imperatives. The system fundamentally requires strict adherence to ACID (Atomicity, Consistency, Isolation, Durability) properties to ensure that no extracted tasks are lost or corrupted during the highly concurrent, asynchronous processing pipeline. Furthermore, PostgreSQL offers superior, native support for advanced temporal data types (specifically `TIMESTAMP WITH TIME ZONE`), which are absolutely critical for a system predicated on time-sensitive event management and proactive notifications across diverse geographic locations. The schema is highly normalized to the Third Normal Form (3NF) to eliminate data redundancy and ensure referential integrity across the microservice ecosystem.

### 2. SQLAlchemy Models and ORM Integration

To interface the Python-based FastAPI backend with the PostgreSQL database, the architecture employs SQLAlchemy, an advanced Object Relational Mapper (ORM). The utilization of an ORM abstracts the underlying SQL dialects and translates complex database operations into programmatic, object-oriented Python paradigms. This abstraction provides several profound advantages. First, it completely neutralizes the risk of SQL injection vulnerabilities, as the ORM handles parameter binding natively. Second, it allows the engineering team to define the database schema purely in Python code. These programmatic models serve as the single source of truth for the data structures. Accompanying the ORM is the `Alembic` library, which provides a robust framework for managing progressive database schema migrations, ensuring that as the Chatnalyxer feature set evolves, the underlying database structure can be safely and incrementally modified without requiring catastrophic data wipes or extensive downtime.

### 3. The User Table Architecture

The `User` table serves as the primary anchor point for all relational data within the system. To ensure absolute uniqueness and mitigate the security risks associated with sequential integer IDs (such as Insecure Direct Object References), the primary key for the User table is implemented utilizing a Universally Unique Identifier (UUID v4). The table schema includes standard authentication vectors, notably the user's primary email address (enforced with a unique constraint) and their cryptographic password hash. Critically, the raw password is never stored; instead, a highly salted Bcrypt hash is persisted. The table also houses the user's Expo Push Notification token, which is essential for routing alerts to their specific physical device. Additionally, the table maintains granular user-specific configuration preferences, allowing individuals to customize their notification behavior (e.g., opting out of low-priority alerts) without altering the global application state.

### 4. The Task Table Architecture

The `Task` table represents the core transactional entity of the Chatnalyxer system, serving as the ultimate repository for the data extracted by the Gemini LLM pipeline. Like the User table, it utilizes a UUID as its primary key. The schema is rigorously defined to ensure data consistency. It includes a `title` column (a concise string representation of the event), a `description` column (optional, for additional context derived from the chat), and most importantly, the `due_date` column, strictly enforced as a timezone-aware UTC timestamp. Furthermore, the table incorporates an `Enum` type column for `priority_level` (restricted to HIGH, MEDIUM, or LOW), mapping directly to the LLM's heuristic output. To provide the user with context regarding the origin of the automated extraction, the table includes a `source_group_jid` string, identifying the specific WhatsApp group where the deadline was discussed. Finally, a boolean `is_completed` flag enables the state management of the task within the mobile application's UI.

### 5. The Notification Table Architecture

To manage the proactive engagement features of the system, a dedicated `Notification` table works in tandem with the scheduling service. This table prevents notification duplication and tracks the delivery status of outbound alerts. Its schema includes a `send_at` timestamp column, dictating the precise moment the alert should be dispatched by the APScheduler. An `Enum` status column tracks the state of the notification (`SCHEDULED`, `DELIVERED`, `FAILED`). Furthermore, this table includes a `payload_type` indicator, defining whether the notification is a silent background update, a standard alert, or a persistent, alarm-style high-priority interruption. By persistently tracking this data, the system can audit its notification delivery reliability and implement exponential backoff or retry logic if the external Expo Push Notification servers experience transient outages.

### 6. Relational Architecture and Constraints

The integrity of the Chatnalyxer database relies on a rigorously defined relational architecture enforced through strict foreign key constraints at the database level. The primary relationship is a One-to-Many mapping between the `User` table and the `Task` table; a single user can possess an infinite number of extracted tasks, but every task must be indelibly linked to exactly one user via a `user_id` foreign key. Similarly, there is a One-to-Many relationship between the `Task` table and the `Notification` table, as a single critical deadline may trigger a cascade of scheduled alerts (e.g., a 24-hour warning, a 2-hour warning, and a 15-minute final alert). These relationships are configured with cascading delete rules (`ON DELETE CASCADE`). This is a critical privacy feature; if a user initiates an account deletion request through the mobile application, deleting their row in the User table will instantaneously and automatically obliterate all associated tasks, sessions, and notification records across the entire database, ensuring total data eradication without requiring complex application-layer logic.

### 7. Indexing Strategy for Temporal Queries

Given that the core utility of Chatnalyxer is dependent on time-sensitive event management, querying the database efficiently is paramount. The internal Scheduling Service operates as a continuous background daemon, aggressively polling the database to identify tasks whose deadlines are approaching the current temporal threshold. If unindexed, these continuous sequential table scans would severely degrade the performance of the entire database as the volume of extracted tasks grows. To mitigate this, the architecture implements a highly optimized B-Tree indexing strategy. A composite index is applied to the `user_id` and `due_date` columns within the `Task` table. This allows the PostgreSQL query optimizer to perform ultra-fast range queries (e.g., `SELECT * FROM tasks WHERE due_date BETWEEN NOW() AND NOW() + INTERVAL '24 hours'`) in logarithmic time complexity (O(log n)), ensuring that the scheduling engine remains highly performant and responsive even when managing millions of concurrent tasks across thousands of users.

### 8. The Storage Strategy and Data Minimization

The overarching storage strategy of Chatnalyxer is defined by a philosophical adherence to aggressive data minimization. The system is designed to act as an organizational extraction engine, not an archive of personal communication. Therefore, it is a strict architectural constraint that the Persistent Storage Layer never houses raw chat messages, original conversational text, or the binary blobs of downloaded media (images, PDFs, or audio notes). The PostgreSQL database stores only the structured metadata output by the LLM pipeline (the task name, date, time, and priority). By actively refusing to store the highly sensitive, unencrypted conversational data, the system mathematically immunizes itself against catastrophic privacy breaches. If a malicious actor were to successfully exfiltrate the entire PostgreSQL database, they would obtain a disjointed list of calendar events, rather than the sensitive personal chat histories of the user base.

### 9. Data Lifecycle and Archival Mechanics

To maintain optimal database performance and limit the financial costs associated with cloud storage, Chatnalyxer implements a robust data lifecycle and archival policy. Over time, active users will accrue thousands of completed or expired tasks, which provide no immediate utility to the scheduling engine but inflate the size of the active B-Tree indices. Rather than executing hard deletes on these records (which would destroy the user's historical productivity data), the system utilizes a soft-delete and archival workflow. Tasks marked as `completed` by the user, or tasks whose `due_date` has passed by a predetermined threshold (e.g., 30 days) without completion, are programmatically migrated from the active `Task` table to an identically structured, but unindexed, `TaskArchive` table (or partitioned logically within PostgreSQL). This ensures that the active tables queried by the high-frequency scheduling daemon remain extremely lightweight and fast, while preserving the historical data for the user should they wish to review their past academic or professional performance within the mobile application.

### 10. Security Posture and Encryption

The final pillar of the Database Layer is its uncompromising security posture. Security is enforced at multiple tiers within the storage architecture. At the infrastructure level, the PostgreSQL volume utilizes transparent Encryption at Rest, managed by the cloud provider's Key Management Service (KMS), utilizing AES-256 encryption. This ensures that physical theft of the storage medium yields unreadable cipher text. At the transport level, all communication between the FastAPI backend instances and the database cluster is mandated to occur over SSL/TLS encrypted connections, mitigating the risk of packet sniffing within the internal Virtual Private Cloud (VPC). Within the schema itself, Row-Level Security (RLS) policies can be implemented to ensure that a database query executed within the context of User A can mathematically never retrieve the tasks belonging to User B, providing a final, database-native layer of defense against application-level authorization vulnerabilities.
