# III. SYSTEM ARCHITECTURE

This section provides a rigorous, in-depth architectural deconstruction of the Chatnalyxer system. The architecture is engineered to address the distinct challenges of high-volume, multi-modal data ingestion, real-time semantic processing, and secure, cross-platform state management. The system is fundamentally designed as a distributed, microservices-based application, segregating concerns across distinct computational layers to ensure scalability, fault tolerance, and strict adherence to data privacy principles.

## A. Overall Architecture Overview

The macro-level architecture of Chatnalyxer is predicated on the principles of modularity and separation of concerns, dividing the computational workload across four primary pillars: the Data Ingestion Layer, the Artificial Intelligence (AI) Processing Layer, the Persistent Storage Layer, and the Client Presentation Layer. To accommodate the disparate technical requirements of maintaining a persistent WebSocket connection with the WhatsApp network and executing computationally intensive machine learning models, a polyglot microservices approach was adopted. 

The Data Ingestion Layer is constructed using a Node.js runtime environment. This decision was driven by the inherently asynchronous, event-driven architecture of Node.js, which is optimally suited for managing persistent, high-throughput WebSocket connections with minimal memory overhead. Conversely, the AI Processing Layer is built upon a Python-based FastAPI framework. Python was selected due to its unparalleled ecosystem for machine learning integration, robust data manipulation libraries, and native compatibility with cloud-based AI SDKs. 

These microservices operate concurrently and are decoupled, communicating exclusively through a secure, internal RESTful API boundary. This segregation ensures that a spike in incoming message volume does not linearly degrade the performance of the AI extraction engine, and conversely, latency spikes in the LLM processing pipeline do not cause timeouts or disconnections in the WhatsApp ingestion layer. The overarching design philosophy emphasizes "ephemeral processing," wherein the system ingests unstructured, highly sensitive personal data, structures it autonomously, and immediately discards the raw input, prioritizing user privacy at the architectural level.

## B. Component Interactions

The interactions between the discrete components of the Chatnalyxer architecture are meticulously orchestrated to balance real-time responsiveness with asynchronous background processing. The interaction lifecycle commences at the Client Presentation Layer (the React Native mobile application). The mobile application interacts with the FastAPI backend primarily through synchronous, authenticated HTTPS requests to perform state-altering operations, such as account creation, configuration of whitelisted group chats, and task management.

However, the core functionality of the system—the passive monitoring and extraction of tasks—relies on a highly asynchronous interaction model. When a user successfully links their WhatsApp account, the FastAPI backend issues an asynchronous command to the Node.js Data Ingestion Layer to spawn an isolated worker process dedicated to that user's session. This Node.js worker maintains a persistent connection with the WhatsApp servers. 

When a message is received on the WhatsApp network, the interaction flows unidirectionally from the Node.js service to the Python backend via an internal HTTP POST request (a WebHook mechanism). The FastAPI backend acknowledges receipt of the payload immediately, returning a 202 Accepted status code to the Node.js service to prevent blocking the WebSocket event loop. The payload is then placed into an internal processing queue within the Python environment. Background task workers consume this queue, executing the interactions with the external Azure AI Services and the Google Gemini API. Finally, when the AI pipeline successfully extracts a temporal event, the background worker interacts with the Persistent Storage Layer to commit the record and subsequently interacts with the Push Notification Engine to alert the mobile client.

## C. Data Flow

The flow of data through the Chatnalyxer ecosystem is designed to transform chaotic, multi-modal conversational inputs into structured, actionable organizational outputs while minimizing the geographic and temporal footprint of sensitive information. The data lifecycle is characterized by the following sequential phases:

1) **Ingestion and Decryption**: Raw bytes representing an incoming WhatsApp message arrive at the Node.js ingestion service via the WebSocket connection. The Baileys library decrypts the Signal protocol payload, resulting in a structured JSON object representing the message metadata and content.
2) **Triage and Filtration**: The system evaluates the metadata (specifically the `remoteJid` or group ID) against the user's explicit whitelist. If the message originates from an unauthorized chat, the data flow terminates immediately, and the payload is dropped from memory.
3) **Payload Extraction and Routing**: For authorized messages, the system isolates the payload. If the payload is text, it is packaged into an internal WebHook schema. If the payload contains media (an image, audio file, or PDF document), the Node.js service downloads the encrypted media blob, decrypts it using the accompanying media keys, and temporarily buffers the raw file before transmitting it to the Python backend alongside the metadata.
4) **Multi-Modal Preprocessing**: Upon arrival at the FastAPI backend, the data flow bifurcates based on the MIME type of the payload. Media files are routed to their respective Azure AI endpoints (OCR, Speech-to-Text, or Document Intelligence) for translation into flat text. 
5) **Semantic Extraction**: The resulting text, whether natively typed or derived from media, is synthesized into a standardized prompt structure and transmitted to the Google Gemini LLM API for zero-shot semantic analysis.
6) **Structuring and Persistence**: The LLM returns a strictly formatted JSON response detailing the extracted task. This unstructured-to-structured transformation boundary is critical. The original raw text and any associated media files are immediately purged from memory and the local file system. Only the structured output (Task Name, Date, Time, Priority) flows into the PostgreSQL database.
7) **Triggering**: The newly structured data flows into the scheduling engine, which calculates notification delivery times and dispatches the final payload to the Expo Push Notification servers.

## D. User Authentication

Given the highly sensitive nature of both personal calendar data and private messaging streams, Chatnalyxer employs a rigorous, bifurcated authentication architecture. The system must authenticate the user's identity concerning the Chatnalyxer application itself, and it must separately manage the authentication state between the system and the external WhatsApp network.

For application-level authentication, the FastAPI backend implements a stateless, token-based authentication mechanism utilizing JSON Web Tokens (JWT). Upon initial registration or login via the mobile application, the backend verifies the user's credentials (hashing passwords utilizing the bcrypt algorithm with a computationally expensive work factor). A short-lived JWT access token and a long-lived refresh token are generated and securely transmitted to the client. The React Native application stores these tokens utilizing encrypted secure storage mechanisms native to the respective operating systems (iOS Keychain and Android EncryptedSharedPreferences). Subsequent API requests require the JWT to be passed in the HTTP Authorization header as a Bearer token, ensuring stateless, verifiable communication.

WhatsApp network authentication represents a separate, significantly more complex paradigm. Chatnalyxer acts as a linked companion device. Authentication is initiated via a QR code displayed within the mobile application. This QR code encodes a public identity key and a unique client ID generated by the Node.js ingestion service. When the user scans this code using their primary WhatsApp application on their smartphone, an exchange of cryptographic keys occurs. The Node.js service securely saves the resulting authentication state—comprising noise keys, signed identity keys, and session tokens—into the PostgreSQL database. This persistent storage allows the Node.js service to seamlessly reconnect to the WhatsApp network in the event of a server restart or network interruption without requiring the user to repetitively scan a QR code.

## E. WhatsApp Integration

The integration with the WhatsApp network is facilitated by the `Baileys` library, a robust, unofficial TypeScript/Node.js implementation of the WhatsApp Web API. The decision to utilize this library rather than the official WhatsApp Cloud API was driven by fundamental architectural requirements. The official API is explicitly designed and strictly regulated for commercial business-to-consumer (B2C) communication; it prohibits the passive monitoring of standard user group chats and imposes prohibitive financial costs per message. By acting as a standard companion device, Chatnalyxer preserves the user's ability to monitor their organic, personal group chats without violating the commercial terms of the official enterprise API.

The Node.js integration service operates by establishing a secure WebSocket (WSS) connection to the WhatsApp servers. Once authenticated, the service subscribes to the `messages.upsert` event stream. The architecture here is inherently event-driven. The service acts as a continuous listener, intercepting cryptographic stanzas as they arrive in real-time. 

A critical component of this integration is the filtering mechanism. Because a typical user may be a participant in dozens of high-volume group chats (e.g., family groups, casual social groups) that are irrelevant to academic or professional task management, processing every incoming message would be computationally wasteful and represent a severe privacy overreach. The Node.js service maintains a locally cached, in-memory Hash Map of authorized group IDs. When a `messages.upsert` event fires, the service performs an O(1) time complexity lookup against this Hash Map. If the group ID is absent, the event is immediately discarded at the ingestion layer, ensuring that personal, unauthorized conversations never propagate to the AI processing layer or touch the persistent storage medium.

## F. AI Processing Pipeline

The Artificial Intelligence Processing Pipeline constitutes the computational nucleus of the Chatnalyxer architecture. It is responsible for the complex task of multi-modal data unification and contextual semantic extraction. This pipeline, housed within the FastAPI backend, is executed asynchronously by background worker threads to ensure high throughput and non-blocking API performance.

The pipeline initiates at the **Triage Layer**, which inspects the MIME type of the incoming WebHook payload to route the data to the appropriate processing subsystem.

For text-based payloads, the data bypasses the media processing layer entirely. However, modern communication frequently relies on rich media. The **Image Processing Pipeline** utilizes the Azure AI Vision Optical Character Recognition (OCR) API. When an image (e.g., a photograph of a whiteboard schedule) is received, it is transmitted to the Azure endpoint. The OCR engine identifies text bounding boxes and performs a spatial flattening algorithm, converting the visual arrangement of characters into a sequential, top-to-bottom, left-to-right textual string, preserving the logical flow of the document as much as possible.

Similarly, the **Document Processing Pipeline** handles PDF files, which are frequently used to distribute course syllabi or project briefs. The Azure Document Intelligence API is employed here, as it goes beyond simple OCR by utilizing deep learning models to understand document structure—extracting tables, key-value pairs, and hierarchical headers, converting complex documents into standardized, machine-readable text.

The **Audio Processing Pipeline** intercepts voice notes. These encrypted `.ogg` or `.opus` files are decrypted and transmitted to the Azure Cognitive Speech service. The Automatic Speech Recognition (ASR) engine transcribes the multi-lingual audio into text. Given the disfluent and noisy nature of conversational speech, this transcription is often devoid of standard punctuation, placing a heavier burden on the downstream semantic engine.

Regardless of the initial modality, the resulting unified text string is channeled into the **Gemini LLM Core**. Here, a highly sophisticated prompt engineering methodology is deployed. The prompt is not merely a request for extraction; it is a contextually injected execution environment. The FastAPI backend programmatically calculates the precise UTC timestamp of the message creation event and injects it into the system prompt. The prompt instructs the Google Gemini model to act as a deterministic information extraction agent. It provides the message text and the specific UTC reference time. The LLM is instructed to identify if the text contains an actionable task or temporal event. Crucially, by possessing the exact reference time, the LLM can accurately resolve hyper-informal relative expressions—such as translating "the day after tomorrow at 5" into a precise ISO-8601 timestamp. To mitigate the risk of LLM hallucination and ensure compatibility with the relational database, the prompt enforces a strict JSON schema output. The LLM must return either `null` (if no task is present) or a JSON object containing the `task_name`, `iso_datetime`, and a calculated `priority_level`.

## G. Database Layer

The Persistent Storage Layer is architected utilizing PostgreSQL, a highly robust, open-source relational database management system. PostgreSQL was selected for its adherence to ACID (Atomicity, Consistency, Isolation, Durability) compliance, its superior handling of concurrent read/write operations, and its advanced indexing capabilities for temporal data. The FastAPI backend interfaces with the database utilizing SQLAlchemy, a comprehensive Object Relational Mapper (ORM), which abstracts raw SQL queries into programmatic Python objects, mitigating the risk of SQL injection vulnerabilities and simplifying schema migrations via the Alembic library.

The database schema is normalized to the third normal form (3NF) to minimize data redundancy. The architecture revolves around three primary entities: `Users`, `WhatsAppSessions`, and `Tasks`. The `Users` table stores securely hashed authentication credentials and user-specific configuration preferences. The `WhatsAppSessions` table stores the serialized cryptographic keys required by the Node.js ingestion service to maintain persistent WebSocket connections, encrypted at rest. 

The `Tasks` table is the core repository for the extracted organizational data. It contains foreign key constraints linking each task to its originating user. The table architecture strictly forbids the storage of raw message content or media binaries to enforce the ephemeral processing philosophy. It stores only the structured output of the LLM: the task description, the precise temporal deadline (stored as a timezone-aware UTC timestamp), the identified priority level, and the originating group chat name for contextual reference. B-tree indexing is applied specifically to the deadline timestamp column, optimizing the performance of the scheduling engine, which must frequently query the database to identify tasks whose deadlines are rapidly approaching.

## H. Mobile Application

The Client Presentation Layer is implemented as a cross-platform mobile application developed utilizing the React Native framework in conjunction with the Expo toolchain. This architectural decision enables the deployment of highly performant, native-feeling applications to both iOS and Android operating systems from a single, unified TypeScript codebase. 

The design philosophy of the mobile application prioritizes a reduction in cognitive load, employing a minimalist, Glassmorphism-inspired User Interface (UI) that presents information clearly without overwhelming the user. The application state is managed utilizing robust state management libraries, ensuring that the UI remains synchronously updated with the backend data in real-time. 

The primary interface is a chronologically organized dashboard that visualizes upcoming extracted tasks. The application communicates with the FastAPI backend via secure REST API calls, fetching the structured data from the PostgreSQL database. The mobile application allows the user to exert control over the automated system; users can manually edit extracted tasks, mark them as complete, or adjust their priority levels. Furthermore, the application serves as the configuration hub for the WhatsApp integration, providing the interface through which the user scans the authentication QR code and explicitly toggles the tracking status of their various group chats, thereby enforcing user consent at the edge of the network.

## I. Notification Engine

The Notification Engine bridges the gap between passive extraction and active user engagement. Unlike traditional calendar applications that rely on passive checking, Chatnalyxer employs a proactive notification architecture designed to interrupt the user only when critically necessary. The system utilizes the Expo Push Notification service, which abstracts the complexities of interfacing directly with Apple Push Notification service (APNs) and Firebase Cloud Messaging (FCM), providing a unified API for cross-platform delivery.

The notification architecture implements priority-based routing and formatting. When a deadline approaches, the FastAPI backend constructs a specific notification payload. The structure of this payload is dynamically dictated by the priority level assigned to the task by the Gemini LLM during the extraction phase. 

For routine, low-priority tasks (e.g., a reminder to read a specific chapter), the engine dispatches a standard, silent notification that updates the application badge count and appears in the device's notification center without triggering an auditory alert. For medium-priority tasks, a standard push notification with a default sound is generated. However, for critical, high-priority deadlines (e.g., a major project submission due in two hours), the engine utilizes advanced OS-level notification channels to trigger an alarm-style, persistent notification. These high-priority alerts are designed to bypass standard "Do Not Disturb" parameters where permitted by the operating system, ensuring that critical temporal events successfully capture the user's attention. The notifications also embed deep links and action buttons, allowing the user to mark a task as complete directly from the lock screen without opening the application, further reducing interaction friction.

## J. Scheduling Service

The seamless delivery of proactive notifications relies heavily on the Scheduling Service, implemented within the FastAPI backend utilizing the `APScheduler` (Advanced Python Scheduler) library. APScheduler operates as an in-process background daemon, executing scheduled cron-like jobs without requiring external message brokers like Celery or Redis, thereby simplifying the deployment architecture.

The primary responsibility of the Scheduling Service is the dynamic calculation and orchestration of temporal triggers. The service does not simply set a single alarm for the exact moment a task is due; it executes a sophisticated look-ahead algorithm. A continuous background job polls the PostgreSQL database at defined intervals, scanning the indexed timestamp column for tasks with approaching deadlines.

When a task enters the temporal threshold (e.g., 24 hours before the deadline), the Scheduling Service calculates the optimal delivery schedule based on the task's priority and the user's customized notification preferences. It spawns specific, one-off trigger events scheduled to fire at precise intervals leading up to the deadline (e.g., a warning at 24 hours, a reminder at 12 hours, and a critical alert at 2 hours). The Scheduling Service is meticulously engineered to handle complex edge cases, such as dynamic timezone conversions—ensuring that a user traveling across time zones receives notifications accurately relative to their current local time—and graceful handling of server reboots, ensuring that persistent jobs are safely restored from the database upon application startup. This service ensures the passive monitoring system reliably translates into active, timely intervention.
